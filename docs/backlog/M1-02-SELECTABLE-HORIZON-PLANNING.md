## Outcome

The owner can select how many of the next 1–7 days to plan and maintain that
training plan on a `390x844` mobile viewport. Sessions and activities work for
arbitrary sports, and every explicit save preserves the previously accepted
plan version.

## Proposed 390px user flow

1. Open **Plan**.
2. Select how many next days to plan from 1 through 7 and confirm the start
   date, defaulting to today.
3. See exactly the selected number of consecutive honest date sections with
   training or rest/empty state.
4. Choose a date and add a session.
5. Enter title, sport/domain, intent, expected duration, and optional note.
6. Add zero or more ordered activities with a measurement mode, target, units,
   instructions, and optional alternatives.
7. Reuse a personal activity or create one inline without searching a global
   catalog.
8. Review the selected horizon and changed sessions, then choose **Save plan**.
9. FitTip creates the next immutable manual plan version and returns to the
   current plan.
10. The owner may later edit, move, duplicate, lock/unlock, or remove future
   content. Each accepted save creates another version.

## Scope

- Authenticated `/home/plan` route and mobile-first 1–7-date view.
- Visible day-count selector constrained to 1 through 7.
- Empty selected-horizon creation and date navigation within the approved
  range.
- Create/edit/move/duplicate/remove future sessions.
- Create/reuse/edit/archive personal activity definitions for future use.
- Ordered session activities using the accepted M1-01 measurement contract.
- Training and rest/empty dates without inventing fake sessions.
- Session and activity locks, with explicit owner unlock/edit behavior.
- Unsaved-change protection, stale-version conflict handling, and retry-safe
  server actions.
- Concise validation/error states and keyboard/touch accessibility.
- Automated domain, route/action, component, and 390px browser tests.

## Rules

- Only future or current uncompleted content may be changed through planning.
- Past accepted versions remain viewable through the history capability owned
  by M1-04.
- Removing an item from a new version never deletes it from an older version.
- A personal activity edit affects future reuse only; the saved plan snapshot
  stays unchanged.
- The UI must not default to strength terminology or require sets/reps/load.
- Save is an explicit user action. There is no silent autosave of accepted
  plans.
- No AI or background process creates or changes plan content.

## Non-goals

- AI plans, roadmap generation, proposals, alternatives generated by a model,
  coaching chat, or replanning.
- Training completion/logging, plan-versus-actual history, goals, memory, or
  intake.
- Recurring schedules, calendar sync, drag-and-drop as a required interaction,
  templates, social sharing, or notification scheduling.
- Global activity/exercise content, videos, or sport-specific evaluators.
- Friend data, public registration, analytics, or commercial use.

## Acceptance criteria

1. At `390x844`, the owner can select 1, 3, or 7 days and create a plan with
   exactly that many consecutive date sections without horizontal overflow.
2. Values below 1 or above 7 and a returned date count that differs from the
   request fail safely.
3. The owner can plan examples for running, football skill, mobility, strength,
   and a custom activity without schema or UI assumptions excluding them.
4. Saving creates a new immutable plan version, including the requested day
   count, and preserves the previous one.
5. The owner can move a future session to another date inside the selected
   horizon and remove it in a new
   version without changing history.
6. The owner can create/reuse a personal activity and historical snapshots do
   not change when its definition is edited.
7. Session/activity order and locks persist.
8. A stale browser save receives a clear conflict and does not overwrite the
   newer current plan.
9. Anonymous and cross-user access remain denied.
10. Loading, empty, validation, save-failure, and retry states are honest.
11. No AI, external analytics, secret, or global exercise library is added.

## Open product and UX decisions

1. **Day-count default.** The approved range is 1–7. Recommendation: default
   first use to 7 and remember the last selection thereafter; the selector is
   always visible before plan creation.
2. **Start date.** Recommendation: default to today and let the owner select
   another start date.
3. **Primary layout.** Recommendation: vertical selected-horizon list on
   mobile; desktop may add a wider multi-day treatment.
4. **Save model.** Recommendation: explicit **Save plan** plus changed-item
   summary; no autosave of accepted content.
5. **Rest representation.** Recommendation: an empty date says **No training
   planned**; an explicit rest session is optional and carries intent.
6. **Activity entry.** Recommendation: create inline, with recent personal
   activities offered only after the owner has created them.
7. **Move interaction.** Recommendation: accessible date selector first;
   drag-and-drop is not required.
8. **Locks.** Recommendation: visible lock per session/activity with clear
   wording that it protects future automated replans, not the owner's explicit
   edit.
9. **Limits and copy.** Approve field limits, maximum sessions/activities,
   duration/unit behavior, destructive confirmations, and conflict copy.
